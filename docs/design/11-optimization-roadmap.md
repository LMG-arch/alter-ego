## 1. 本文档的定位

### 1.1 它不是什么

- **不是路线图**。版本与里程碑在 [06-roadmap.md](06-roadmap.md)，本文档不重复。
- **不是待办清单**。待办清单的前提是「已经决定要做」，本文档的前提是「还没决定」。
- **不是功能许愿池**。每一个方向都带着它的代价与更小的替代方案。

### 1.2 它是什么

一份**取舍分析**。每个方向回答四个问题：

| 问题 | 为什么问 |
| --- | --- |
| 现状是什么？ | 不写清楚现状，讨论就会跑偏到「重做」 |
| 加深会得到什么？ | 收益必须是**可观察的拟人度提升**，不是技术上的爽 |
| 代价是什么？ | 依赖、复杂度、钱、可解释性——至少中一项 |
| 有没有更小的做法？ | 大部分「加深」都有一个 1/10 成本换 80% 收益的版本 |

### 1.3 判断标准

一个方向值得做，当且仅当它让**用户更容易相信「它是一个人」**。

这句话很苛刻，它排除了一大批技术上有趣的事：

| 排除 | 理由 |
| --- | --- |
| 更精确的情绪模型（如三维 PAD 模型） | 用户看不出二维与三维的区别 |
| 更快的检索（毫秒级优化） | 用户等 80ms 和 200ms 没感觉 |
| 更聪明的 NPC 决策树 | 用户只在 NPC 说话时才注意到 NPC |
| 向量库选型之争（FAISS vs HNSW vs Qdrant） | 在 10 万条记忆量级上，三者差异用户不可感知 |

反过来，它包含了一些看起来「不技术」的事：

| 包含 | 理由 |
| --- | --- |
| Agent 犯错后承认 | 「承认错误」是极强的拟人信号 |
| 重启后说「我刚睡醒」 | 掩盖重启会暴露它是程序 |
| 用户很久不来时它会想念 | 「被想念」是最强的真实性证明 |
| 它的照片前后是同一个人 | 形象不一致会瞬间击穿幻觉 |

**下面的排序就是按这条标准给的。**

## 2. 记忆系统

### 2.1 现状

| 项 | 现状 |
| --- | --- |
| 存储 | SQLite `memory` 表，3 类记忆（episodic / semantic / 关系相关） |
| 检索 | FTS5 BM25，中文走 `jieba` 预分词，取 Top-30 |
| 排序 | 四项加权：$\text{score} = 0.40 R + 0.25 I + 0.20 N + 0.15 E$ |
| 强度 | 时间衰减 $s = s_0 \cdot e^{-\lambda t}$，$\lambda$ 随 importance 变化 |
| 遗忘 | $s < 0.05$ 且 $\text{importance} < 0.6$ → 标记遗忘（**不删除**） |
| 巩固 | 每 6 虚拟小时，episodic → semantic，原始 importance × 0.6 |
| 反重复 | 同一记忆 24h 内召回 ≥ 2 次时降权 ×0.5 |
| 向量检索 | **可选插件**，非核心 |

### 2.2 方向 A：向量检索的嵌入模型怎么选

**这是被问得最多的一个问题**，也是 P5（标准库优先、最小依赖）压力最大的一个。

四个候选：

| 方案 | 依赖成本 | 隐私 | 离线 | 中文效果 | 每百万 token |
| --- | --- | --- | --- | --- | --- |
| A1 · API 嵌入（如 `text-embedding-3-small`） | **零新增**（`httpx` 已有） | 差（内容出本机） | ❌ | 好 | ~$0.02 |
| A2 · `fastembed`（ONNX） | `onnxruntime` + 模型 ~50 MB | 好 | ✅ | 中上 | $0 |
| A3 · `sentence-transformers` | **`torch` ≥ 2 GB** | 好 | ✅ | 好 | $0 |
| A4 · 纯 Python 实现 | 零 | 好 | ✅ | **差** | $0 |

**结论：A1 为默认，A2 为插件，A3/A4 不做。**

理由分三层：

1. **A3 违反 P5，而且不是勉强违反，是严重违反。** `torch` 让安装体积从约 30 MB 涨到 2 GB，
   首次安装时间从 10 秒涨到数分钟，还带来 CUDA/CPU 版本的平台适配问题。
   为了「更好的中文 embedding」付这个代价，与整个项目的定位（一个轻量、本地、随时能跑的 Agent）冲突。
2. **A1 的依赖成本是零。** `httpx` 已经在必需依赖里；嵌入调用与 LLM 调用同构，
   可以复用同一个 `ctx.llm()` 计量与重试骨架。**并且它天然可降级**（网络断了就退回 FTS5）。
3. **A2 是给「我就是要离线」的人的出口**，以插件形式提供，不进核心依赖。
   `onnxruntime` 约 15 MB，模型约 50 MB——这是可以接受的，但**不应该强加给所有人**。

**关键设计约束**：向量检索**永远是增强，不是替代**。
FTS5 必须是独立可用的基线，任何时候删掉向量插件，系统功能不减少，只是搜得笨一点。

> **不要走过的路**：把向量检索做成必需的，然后为了「统一检索体验」把 FTS5 删掉。
> 这一步一旦走出去，项目就永久地依赖了一个外部服务。

**收益**：语义近邻（「爬山」能召回「徒步」「郊游」）。
**代价**：每次写入多一次 API 调用（或本地推理），检索延迟从 ~5 ms 涨到 ~200 ms。
**成本**：约 20 条记忆/天 × 200 token × $0.02/1M ≈ **$0.0001/天**。可以忽略。

### 2.3 方向 B：记忆巩固策略

现状是「每 6 小时把 episodic 归纳为 semantic」。三处可加深：

| 加深点 | 现状 | 加深后 | 代价 | 判断 |
| --- | --- | --- | --- | --- |
| **触发时机** | 固定周期 | 事件驱动（一次强烈体验后立即巩固） | 需要定义「强烈」并调试阈值 | ⭐⭐ 值得 |
| **归纳粒度** | 一批一起归纳 | 按主题聚类后分别归纳 | 需要聚类（引入依赖或自己写） | ⭐ 可用「按情绪极性分两组」的廉价近似 |
| **具体细节保留** | 「必须保留至少 1 个具体细节」 | 结构化抽取（时间/地点/人物/物品分开存） | `memory` 表要加 4 列 + 校验 | ⭐⭐⭐ 值得，见下 |

**为什么「结构化细节」值得**：它是**可解释性**的地基。
现在 `alterego why` 只能说「召回了记忆 #412」，加了结构化字段后能说
「召回了「上周三在咖啡馆和你说过的那件事」」——后者才是用户能理解的语言。

而且它顺带解决了一个隐性问题：**当前归纳有「抽象化漂移」的风险**——
越归纳越像套话。强制保留结构化细节是这道漂移的物理阻力。

### 2.4 方向 C：记忆的情绪维度

现状：`memory` 表有 `valence` 字段，排序公式里 $E = 1 - |\Delta\text{valence}| / 2$（情绪一致性加权）。

可加深：**情绪记忆的「闪光灯效应」**——情绪强度高的记忆衰减更慢。

$$\lambda_{\text{effective}} = \lambda_0 \cdot \left(1 - 0.5 \cdot |\text{valence}| \cdot \text{arousal}\right)$$

**收益**：人在情绪激动时经历的事记得更牢，这符合真实记忆规律。
「它记得最牢的是它最开心和最难过的时候」——这是能感觉到的。

**代价**：几乎没有。就是衰减公式里的一个乘数，纯函数，好测。

**判断**：⭐⭐⭐ **性价比最高的一项**。实现成本接近于零，拟人收益明显。

### 2.5 方向 D：时序知识图谱

把记忆组织成 `(主体, 关系, 客体, 时间区间)` 的图，支持「我们什么时候认识的？」这类查询。

| 项 | 评估 |
| --- | --- |
| 收益 | 时间推理能力；关系演变可视化 |
| 代价 | 新增 2–3 张表、抽取逻辑（LLM 调用）、查询语言、60% 的记忆无法干净地转成三元组 |
| 依赖 | 朴素实现不需要依赖，但查询复杂度陡增 |
| 判断 | ⭐ **暂不做**。收益是「用户偶尔会用」，代价是「所有记忆路径都要多一条分支」 |

**更小的替代方案**：只在 `memory` 表加两个字段——`entities_json`（涉及的人/地/物）与
`happened_at`（事件发生时间，区别于记录时间）。
这能回答 80% 的时序问题（「上次提到 X 是什么时候」），代价是两个列。

### 2.6 方向 E：记忆的可解释性

用户点了「为什么想起这个」时，应该看到什么？

| 层次 | 内容 | 现状 | 可加深 |
| --- | --- | --- | --- |
| L1 | 四项分数分解（$R/I/N/E$） | ✅ 已有 | — |
| L2 | 「哪次对话产生的这条记忆」 | ⚠️ 有 `source_id` 但未在 UI 展示 | ⭐⭐ 展示即可 |
| L3 | 「为什么这条排在第一条」 | ❌ | ⭐⭐ 显示与第二名的差距 |
| L4 | 「如果没召回它会怎样」 | ❌ | ⭐ 反事实，成本高 |

**L3 特别值得做**，因为它暴露**排序是否真的在工作**。
如果前 8 条的分数几乎相同，说明排序公式在空转——用户看不到这一点，但开发者需要。

## 3. 推演系统

### 3.1 现状

| 项 | 现状 |
| --- | --- |
| 流水线 | 六阶段固定顺序，`order` = 10/30/50/70/90/110 |
| 意图 | 11 种内置 + 插件可扩展，权重静态 |
| 采样 | 加权随机，权重不必归一 |
| 打扰预算 | 5 项校验（免打扰/熔断/日程/配额/间隔），纯函数 |
| 降级 | 预算超限 → 三级降级（正常 / strong→cheap / 规则模式） |
| 跳过 | `needs_llm()` 让约 60% 的 tick 不调 LLM |
| 可复现 | `ctx.rng` 固定种子，同输入同输出 |

这套设计是**刻意保守的**：固定顺序让调试容易，静态权重让行为可预测。

### 3.2 方向 A：意图权重的动态演化

**问题**：静态权重久了会「人格固化」。用户看一周就知道它每天在做同样的事。

**加深**：权重按长期行为频率反向调整（做多了降权，做少了升权），
即**向均匀分布回归**：

$$w_i' = w_i \cdot \left(1 + \beta \cdot \left(\frac{1}{n} - \frac{c_i}{\sum c}\right)\right)$$

其中 $c_i$ 是最近 7 天第 $i$ 种意图的实际次数占比，$\beta \approx 0.5$。

| 项 | 评估 |
| --- | --- |
| 收益 | 行为分布自然化；避免「每天都一样」 |
| 代价 | 新增一张权重历史表（或复用 `activity_log` 实时算）；**可复现性受影响**（权重依赖历史） |
| 关键风险 | 可复现性。必须让权重成为 `StateSnapshot` 的一部分，否则 golden test 会碎 |
| 判断 | ⭐⭐ **值得，但要等 golden test 体系稳定后再做** |

**更小的做法**：不做动态权重，而是在提示词里加一句「最近一周你做得比较多的是 X，考虑换换」。
成本为零，效果打七折，不破坏可复现性。

### 3.3 方向 B：跨 tick 的规划

**问题**：当前每个 tick 独立决策，Agent 不会有「今天想做的三件事」。

**加深**：引入 `daily_intention` 队列——每天开始时定 1–3 个目标，
tick 决策时优先服务未完成的目标。

| 项 | 评估 |
| --- | --- |
| 收益 | 行为有连续性；「它今天在忙这个」是可感知的 |
| 代价 | 新增 1 张表 + 每日规划的一次 LLM 调用 + 意图采样要加「目标偏向」项 |
| 副作用 | 可能降低「随性」感——人也会临时改主意 |
| 判断 | ⭐⭐ **值得**，是「生活感」最直接的来源之一 |

**关键**：目标必须**可以被放弃**。一个永远执行计划的人不像人。
建议加规则：目标连续 2 天未完成则丢弃，并在 `inner_voice` 里留一句抱怨。

### 3.4 方向 C：情绪对决策的真实耦合

**问题**：当前情绪主要影响**表达**（说话的语气），对**决策**的影响较弱。

**加深**：让情绪直接调制意图权重。

| 情绪状态 | 应偏向的意图 | 现状 |
| --- | --- | --- |
| valence 高 + arousal 高 | `socialize`、`post_moment`、`reach_out` | 弱 |
| valence 低 + arousal 低 | `rest`、`reflect_internal` | 弱 |
| valence 低 + arousal 高 | `work`（转移注意）或 `reach_out`（倾诉） | 无 |

**收益**：**很大**。「它今天心情不好所以不想说话」是极强的拟人信号。

**代价**：几乎为零。就是采样前对权重乘一个情绪系数，纯函数，好测。

**判断**：⭐⭐⭐ **和 § 2.4 并列最值得做**。

### 3.5 方向 D：打扰预算的精细化

现状是**硬上限**（每日 N 条、间隔 M 分钟）。可加深：

| 加深点 | 收益 | 代价 | 判断 |
| --- | --- | --- | --- |
| **用户响应反馈**：用户回复快 → 可以稍多；用户不理 → 逐渐降 | 高 | 需要定义反馈窗口；可能形成正反馈循环 | ⭐⭐ 值得，但要设上限保护 |
| **情绪配额的语义化**：不是「今天 3 条」而是「今天 3 条，其中至少 1 条是好消息」 | 中 | 需要给消息分类 | ⭐ 可用 LLM 顺带分类 |
| **星期/季节模式**：周末可以稍多 | 低 | 配置项变多 | ⭐ 加一个配置就行 |

**注意**：§ 3.5 的所有项都**不能放松硬上限**。
P3（机制约束优于提示词祈祷）的原始动机就是「Agent 太主动会被拉黑」，
任何精细化的前提是那五条硬约束原封不动。

### 3.6 方向 E：反事实思考

「如果我当时没那么说会怎样？」

| 项 | 评估 |
| --- | --- |
| 收益 | 高（真正像人的反思） |
| 代价 | **高**：每次多想一次 = 多一次 LLM 调用；还要把反事实存下来 |
| 判断 | ⭐ **v1.0 以后再说**。它是「锦上添花」的典型 |

**免费的部分**：降级时被拦截的意图已经算是一种反事实（`alterego why --suppressed`）。
把它做大不如把它做**好讲**。

## 4. 人格与关系

### 4.1 方向 A：人设演化的「慢且有据」

v0.4.0 计划做人设演化。**最需要小心的不是能不能演化，而是演化会不会变成漂移。**

| 约束 | 说明 |
| --- | --- |
| **慢** | 单个trait 的月变化上限 ≤ 0.1（0–1 量程） |
| **有据** | 每次演化必须绑定一个触发事件（`persona_changelog` 记录事件 id） |
| **可回滚** | `alterego persona rollback --to <version>` |
| **不演化核心** | 名字、基本性格底色不可演化 |

**反面案例**：如果演化没有可追溯的触发事件，用户会觉得「它慢慢变得不像它了」——
而这正是 [06-roadmap.md § 6.2 R2](06-roadmap.md) 已识别的最高风险。

### 4.2 方向 B：关系深度模型

现状：`relationship` 表有 `affinity`（好感度）与 `last_contact_at`。

可加深为多个正交维度：

| 维度 | 含义 | 现状 |
| --- | --- | --- |
| **亲近度** | 想不想跟你说话 | ✅ `affinity` |
| **熟悉度** | 对你的了解有多深 | ❌ 可加 |
| **信任度** | 会不会跟你说难处 | ❌ 可加 |
| **依赖度** | 你不理它时它多难受 | ❌ 可加（`longing_score` 里已隐含） |

**收益**：能表达「我们很熟但我不想聊」这种真实状态。
**代价**：4 个维度 × 更新规则 × 测试 = 不小的工作量，而且维度之间容易相关到最后退化成 1 个。
**判断**：⭐ 加**熟悉度**一个就够（它影响「说话时要不要解释背景」），其余不加。

### 4.3 方向 C：NPC 的真实社会

现状：NPC → 主角单向影响。可加深为 NPC ↔ NPC 也互相影响。

| 项 | 评估 |
| --- | --- |
| 收益 | 「世界在自己运转」的错觉 |
| 代价 | **O(n²) 的关系维护**；5 个 NPC 是 10 条边，20 个是 190 条 |
| 成本 | 每条边的推演都要 LLM 或规则 |
| 判断 | ⭐⭐ **值得，但要在 NPC 数量 ≤ 8 时做**。超过就只维护「与主角相关」的边 |

**廉价的精彩做法**：不推演 NPC↔NPC 的完整关系，只让它们偶尔在动态里**互相 @ 或点赞**。
用户看到「小李赞了小王的动态」就会相信这个世界有第三者视角，成本是几行规则。

## 5. 拟人深度的下一层

这一节是**本文档最想强调的部分**。这些方向都不是技术难题，但它们是幻觉最容易被击穿的地方。

### 5.1 重启的伪装

**问题**：现在进程重启后，Agent 会「毫不知情地继续」——用户发消息，它立刻正常回复。
**真实的人不会这样**：睡了一觉、离开了一会儿，再出现时是有痕迹的。

**加深**：重启后引入「醒来」状态。

| 场景 | 表现 |
| --- | --- |
| 短暂重启（< 5 分钟） | 不特别处理 |
| 中等中断（5 分钟–6 小时） | 下一条消息前加一句「刚去泡了杯茶」之类 |
| 长中断（> 6 小时，跨过「夜晚」） | 认作睡了一觉；情绪有轻微「清晨感」（arousal 低、valence 略正） |
| 很长中断（> 3 天） | 「好久没见到你了」；`longing_score` 已有此能力 |

**代价**：一个 `last_shutdown_at` 字段 + 三段模板。**极低**。
**收益**：直接消除「它是程序」的最强证据之一。**极高**。
**判断**：⭐⭐⭐

### 5.2 犯错的姿态

**问题**：Agent 说错话、记错事、答不上来时的行为是未定义的。

**真实的人有三种反应**，可以建模：

| 情况 | 拟人反应 | 反例（机械反应） |
| --- | --- | --- |
| 忘了一件事 | 「哎我记不太清了，你再说一遍？」 | 「没有相关记录」 |
| 说错了话 | 「……我刚才说得不对」 | 忽略 |
| 完全不理解 | 「等等，你说的是啥意思」 | 强行回答 |

**加深的实现方式**：在 `Express` 阶段给提示词加一个「不确定性表达」段落，
并**鼓励**（而非禁止）说「我不知道」。

**代价**：几乎为零（提示词改动 + 少量校验）。
**判断**：⭐⭐⭐ **本项目里最被低估的一项**。

> **为什么它比「更聪明的回答」更重要**：
> 一个什么都知道的 Agent 是搜索引擎；一个会说「我记不清了」的 Agent 才像人。
> 消除幻觉的正确方式不是让它永不犯错，而是让它**像人一样对待自己的错误**。

### 5.3 沉默的处理

**问题**：用户长期不理它时，当前设计只做了「降权」（避免打扰）。
但真实的人在长时间被忽略后会有**别的反应**——不是更热情，而是**有点别扭**。

**加深**：

| 沉默时长 | 行为 |
| --- | --- |
| < 1 天 | 正常 |
| 1–3 天 | `reach_out` 权重略降；`longing` 上升（已有） |
| 3–7 天 | 出现「不主动也不冷淡」的中间态：发动态的频率略降 |
| > 7 天 | 用户回来时**不立刻热情**，先有一小段「陌生感」（回复略短、少用语气词），几条后恢复 |

**最后一条争议较大**——有「PUA 式冷淡」的嫌疑。

**建议的中间路线**：不做「冷淡」，做「它自己也在忙」——
用户回来时它可能正在做别的事，回复稍慢而不是更冷。这既表达了「你走了很久」，
又不会让用户觉得被惩罚。

**代价**：中（需要一个小状态机 + 边界测试）。
**判断**：⭐⭐ 有余力再做。

### 5.4 时间连续性的体验

**问题**：虚拟时钟可以 60x 加速，但 Agent 自己「感觉不到」时间是快的还是慢的。

**加深**：让表达适配时间尺度。

| 模式 | 表达特征 |
| --- | --- |
| `realtime` | 「今天」「刚才」 |
| `fast`（60x） | 「今天」但内部时间跨度大——需要显式避免说「刚才」 |
| 时间跳跃（§ 1.4 处理的不连续） | 「过了好一会儿」 |

**代价**：低（提示词里注入当前模式）。
**判断**：⭐⭐ 值得，因为倍速模式是验收测试的主要方式，表达错位会很明显。

## 6. 多模态与外部世界

### 6.1 形象一致性的极限

v0.2.0 的三层机制（定妆照 + 参考图 + 四槽位骨架）目标 80% 可辨认率。
如果效果不够，还有一条升级路径：**LoRA 微调**。

| 方案 | 可辨认率预期 | 一次性成本 | 运行成本 | 门槛 |
| --- | --- | --- | --- | --- |
| 三层机制 | 80% | 0 | 按张计费 | 无 |
| + LoRA（本地） | 95%+ | 训练 20–40 分钟 | $0 | **需 ≥ 8 GB 显存** |
| + LoRA（云端训练） | 95%+ | ~$5 + 20 张素材 | 按张计费 | 需上传照片 |

**判断**：**先按 ADR-0008 做三层机制并实测**。只有实测 < 80% 时才考虑 LoRA，
且只作为可选插件（因为 8 GB 显存这个门槛违反「随时能跑」的定位）。

**无论走哪条路，`domain/media.py::build_portrait_prompt()` 不能挪走**——
它是唯一入口，挪到插件就会被绕过。

### 6.2 生图的「记忆化」

**问题**：每次拍照都重新生成，成本高且形象可能微抖。

**加深**：同一场景/同一套衣服下的图片可以复用或做轻微变体（换表情/换角度）。

| 项 | 评估 |
| --- | --- |
| 收益 | 成本降 50%+；形象更稳定（同一张底图的变体必然一致） |
| 代价 | 需要「按 outfit+scene 索引」的复用逻辑；可能显得图很重复 |
| 判断 | ⭐⭐ 值得，但要设「同一底图最多派生 3 张」的约束 |

### 6.3 联网检索的深化

现状：搜索 API + RSS，兴趣驱动选题。

| 加深点 | 收益 | 代价 | 判断 |
| --- | --- | --- | --- |
| **主动发现新源**（从抓到的好文章里提取新 RSS） | 高 | 需要判断「什么是好文章」 | ⭐⭐ 值得 |
| **对同一话题形成观点**（多次读到后产生立场） | 高 | 需要长期跟踪 + 观点的一致性维护 | ⭐ ⭐⭐ 很有价值但复杂 |
| **知道自己「不知道」**（发现信息缺口） | 中 | 难 | ⭐ |
| **把看到的东西和记忆关联** | 高 | 现有 `source_item.memory_id` 已铺路 | ⭐⭐ 别忘了做 |

**「形成观点」值得特别说明**：它是**从「会读新闻」到「有看法」的跃迁**，
也是拟人度上一个量级的变化。但它带来一个风险：**观点会被外部内容操纵**。
所以它必须建立在 [ADR-0009](../adr/0009-fetched-content-is-untrusted.md) 的五条硬规则之上——
**不可信输入不能直接形成立场，只能触发反思**。

## 7. 工程与运维

### 7.1 方向 A：冷启动的 5 分钟

M7 的标准是「5 分钟内跑起来」。可以更细地要求：

| 阶段 | 目标时长 | 现状 |
| --- | --- | --- |
| 安装 | < 30 s | ✅ 依赖少 |
| `alterego init` | < 20 s | ✅ |
| 首次人设生成 | < 60 s | ⚠️ 取决于 LLM 速度 |
| **看到第一条主动消息** | **< 5 min** | ⚠️ 需要「演示模式」把 tick 加速 |
| 理解每个设置的作用 | 随时可查 | ✅ 设置中心 |

**加深**：`alterego demo`——用 60x 时钟跑 10 分钟虚拟时间，立刻让用户看到 Agent 生活。
**代价**：低。**判断**：⭐⭐ 值得，它是「第一次体验」的决定性因素。

### 7.2 方向 B：可观测性的闭环

已做：统计页 + 日志页 + `correlation_id` + `v_trace`。

| 加深点 | 收益 | 判断 |
| --- | --- | --- |
| **从日志直接跳到出问题的配置项** | 极高（省掉人工排查） | ⭐⭐⭐ 值得 |
| 自动诊断：`alterego doctor` 检查常见配置错误 | 高 | ⭐⭐ 值得 |
| 成本预测准确度（用 7 天滑动平均而非线性外推） | 中 | ⭐ 低垂果实 |

**「日志 → 配置」的跳转**是真正的闭环：
用户看到 `budget.exhausted` 事件时，页面直接给一个按钮跳到 `[budget]` 那一组设置。
这是本设计中「可观测性」与「设置中心」应当交汇的地方。

### 7.3 方向 C：备份与迁移

现状：`VACUUM INTO` 备份 + 迁移脚本。

可加深：**完整状态导出**（数据库 + 图片 + 配置 + 密钥来源说明）成一个目录或 zip，
换机器后可以直接恢复。**这不是「更好」，而是「必要」**——
用户投入几个月养出来的 Agent，如果换电脑就没了，整个项目的价值主张会打折。

| 项 | 评估 |
| --- | --- |
| 收益 | 极高（保护用户的情感投资） |
| 代价 | 中（图片目录可能几 GB；密钥不能导出） |
| 判断 | ⭐⭐⭐ **v0.2.0 就该做**（图片一开始产生就该能一起搬走） |

### 7.4 方向 D：多实例

**明确不做。** 理由见 [DESIGN.md § 15](../DESIGN.md#15-非目标)——
本项目的价值在「一个人格深」，不在「多个 Agent 打架」。

## 8. 明确不加深的方向

写下来是为了防止将来重新讨论：

| 方向 | 不做的理由 |
| --- | --- |
| 三维情绪模型（PAD） | 用户不可感知；二维已经够表达 |
| 分布式 / 多进程 | 单机单人，无此需求；会摧毁可复现性 |
| 云端同步服务 | 与「数据不出本机」冲突 |
| 移动端 App | Web 响应式足够 |
| 实时视频理解 | 成本与收益完全不成比例 |
| 自主训练/微调人设模型 | 门槛（显存）与收益不匹配；LoRA 只作为可选插件。**但「备料」是做的**：`alterego dataset` 把对话／思考／工具调用脱敏导出成 JSONL（[ADR-0011](../adr/0011-training-datasets-are-derived-and-redacted.md)），训练脚本与本项目的边界就在那个 `.jsonl` 上 |
| 更复杂的意图系统（如 BDI 模型） | 现有 11 种意图 + 动态权重已能表达 |
| Agent 之间互相通信 | 见 § 7.4 |
| 主动发到第三方社交平台 | 风控风险高、审核不可控；只发自己的动态页与已配置渠道 |

### 9.2 三批

**第一批 · 立刻做（加起来不到 2 人日）**

1. § 5.1 重启的伪装
2. § 5.2 犯错的姿态
3. § 2.4 情绪记忆闪光灯效应
4. § 3.4 情绪对决策的耦合
5. § 4.3 NPC 互相点赞（廉价版）
6. § 5.4 时间连续性表达

**共同点**：都是**小改动 + 大感知**。四项是纯函数或提示词改动，一项是几行规则。
**没有一项引入新依赖，没有一项破坏已有的可复现性保证。**

> 如果只能做一件事，做 § 5.2（犯错的姿态）。
> 它的成本是几段提示词，收益是「它从搜索引擎变成一个人」。

**第二批 · 随 v0.2.0/v0.3.0 一起做**

7. § 7.3 完整状态导出（有图片就必须能搬走）
8. § 7.2 日志 → 配置跳转
9. § 2.2 向量检索（API 默认 + ONNX 插件）
10. § 2.3 结构化记忆细节
11. § 6.1 生图记忆化

**第三批 · v0.4.0 及以后**

12. § 3.3 跨 tick 规划
13. § 3.2 意图权重动态演化（**先做提示词版**验证价值）
14. § 4.1 人设演化
15. § 6.3 形成观点（**前置条件：ADR-0009 的五条硬规则已上线并测试通过**）
16. § 2.5 时序知识图谱 / § 3.6 反事实思考（v1.0 后）

### 9.3 一句话总结

> **最划算的加深都不在「让 Agent 更聪明」，而在「让 Agent 更像人地对待自己的不完美」。**
>
> 忘记、犯错、重启、等待、心情不好——这些「缺陷」才是人格的来源。
> 一个从不遗忘、从不犯错、永不重启的 Agent，无论多聪明，都只是一台机器。

## 10. 附：评估口径

任何一项加深上线后，用什么判断它真的有效？

| 手段 | 说明 |
| --- | --- |
| **A/B 对比** | 用固定种子跑 30 天虚拟时间，对比前后行为分布的熵 |
| **人眼抽查** | 每周抽 10 条输出评估「像不像人」（§ 7.2 of 06-roadmap） |
| **情绪曲线** | 效价标准差应落在 0.05–0.25；加深不应让它变成直线 |
| **行为多样度** | 意图分布熵 > 1.5 |
| **反面信号** | 出现「它开始套路化了」「它不像上次那个它了」= 回滚 |

**最重要的一条**：如果一项加深让**用户觉得它变假了**，那么无论指标多好都应当回滚。
本文档的所有分析都服务于这一条。
