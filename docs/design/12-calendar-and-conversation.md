## 1. 本文档要解决的问题

原始需求里有一句话，本分册整篇都在回答它：

> 保证对话要和谐流畅像人，并且会过节日节日的的时候会根据节日安排流程，
> 并且提前几天就开始安排要保证日程流畅和谐，不要突然过渡到了节日进行休假等，
> 要提前几天就知道过几天是节日

拆成四条**可验证**的要求：

| # | 要求 | 反例（做错了是什么样） | 本分册的对应 |
| --- | --- | --- | --- |
| R1 | 提前好几天就知道要过节 | 9 月 24 日还在正常上班，25 日突然「我回家过中秋了」 | § 4 强度曲线外沿 |
| R2 | 日程是**渐渐**转向节日的 | 节前一天还在排满会议，第二天全清空 | § 5 两个时点 |
| R3 | 节日过后不是瞬间归零 | 节后第一天就完全当没发生过 | § 4 节后衰减 |
| R4 | 两个节日挨着时，不能跳 | 中秋第二天就开始张罗国庆，把中秋余温抹掉 | § 6 支配规则 |

R1–R3 靠**一条曲线**满足，R4 靠**一条选择规则**满足。两者都不需要新的依赖、新的表、新的配置项。

设计原则对应：**P3 机制约束优于提示词祈祷**。R1–R4 都不是靠提示词里写「请提前几天准备」实现的——那种提示词的失效方式是静默的，而曲线失效会当场测试挂掉。

## 2. 节日为什么必须是数据

### 2.1 三类来源，其中一类谁也推不出来

| 来源 | 例子 | 能不能算出来 |
| --- | --- | --- |
| **法条** | 春节法定放假 4 天、国庆节法定放假 3 天 | 能，但要读条文且会修法 |
| **天文事实** | 中秋是农历八月十五、清明是节气 | 能，但需要精度足够的历法实现 |
| **行政决定** | 调休：哪两个周末调成工作日换一个连休 | **不能。这是国务院办公厅每年发一次公告定的** |

第三条是决定性的。2026 年春节放 02-16 ~ 02-19 **不是**任何算法的结论，是行政决定。想「用代码算节假日」的实现最终一定会退化成一张表——只是把表硬编码在 Python 里而不是 TOML 里，顺便丢掉了「这张表可信到什么程度」这个信息。

### 2.2 因此节日是「随包数据 + 纯函数」

```
src/alterego/holidays/
├── __init__.py      读盘（唯一的 IO 入口）
└── 2026.toml        数据
src/alterego/domain/
└── calendar.py      纯函数：把「提前几天」变成可测的曲线
```

这个分工是 **P1 内核无知** 与红线 2（`domain/` 不做 IO）的直接后果：`HolidayCalendar.from_toml(text)` 只吃字符串，谁知道文件在哪谁去读。`tests/test_domain_calendar.py` 因此完全不需要碰磁盘，用的是自己搭的日历。

### 2.3 两个可信度标记

| 标记 | 位置 | 含义 |
| --- | --- | --- |
| `confirmed` | 文件级 | 这一年的**调休与连休区间**是否已按办公厅公告核对 |
| `verified` | 单个节日 | 这个节日的**日期**是否已按权威日历核对 |

出厂状态是 `confirmed = false`。这不是没写完，而是**诚实**：公告没出的时候就是不知道，标成「已核对」才是 bug。用户有权在界面上先看到这件事，而不是某天才发现它一直按错的日期过日子。

农历节日（春节、元宵、清明、端午、中秋）天然是 `verified = false`——日期是推算的；公历固定节日（元旦、劳动节、国庆、情人节、圣诞）是 `true`。`alterego calendar check` 就是把这两类分开列出来。

## 3. 数据文件格式

一年一个文件，文件名就是年份：`holidays/2026.toml`。

```toml
confirmed = false
note = "调休与连休区间待按国务院办公厅公告核对；农历/节气日期待按权威日历核对"

[[holiday]]
id = "spring_festival"           # 稳定标识，小写 ASCII，跨年不变
name = "春节"                     # 给人看的
kind = "statutory"               # statutory | traditional | western | personal
day = 2026-02-17                 # 锚点：节日「正日子」，必须落在 days_off 里
days_off = [2026-02-16, 2026-02-17, 2026-02-18, 2026-02-19]
makeup_days = []                 # 调休补班日
lead_days = 10                   # 提前几天开始有感觉（1 ~ 30）
aftermath_days = 4               # 节后几天还有余温（0 ~ 14）
verified = false
note = "除夕 2026-02-16；农历正月初一 2026-02-17（待核对）；调休 待公告"
prep_activities = ["抢回家的票", "买年货", "收行李", "跟同事说一声"]
during_activities = ["回老家", "走亲戚"]
aftermath_activities = ["返程", "缓一缓"]
```

### 3.1 为什么不复用通用配置

`holidays/*.toml` **不是** `templates/alterego.toml` 的一部分，尽管长得像。区别在于职责：配置文件是「用户可改的运行参数」，节日数据是「出厂知识」。混在一起的后果是用户升级时被问到「要不要保留你改过的春节日期」。所以 `[holiday]` 从未进入 `defaults.toml`（`test_kernel_config.py::test_authoritative_template_covers_every_key` 会挡住误加）。

### 3.2 为什么是 TOML 而不是 YAML

标准库优先（P5）。Python 3.11 起 `tomllib` 内置，YAML 要引第三方。同目录的 `defaults.toml`、`pyproject.toml` 已经是 TOML，编辑器折叠与 diff 行为一致。

### 3.3 校验：宁可在加载时炸

`Holiday.__post_init__` 与 `HolidayCalendar.__post_init__` 拒绝：

| 情况 | 消息片段 | 为什么必须拒绝 |
| --- | --- | --- |
| `id` / `name` 为空 | —— | 空 id 会让「同一个节日」判断失效 |
| `kind` 不在词表里 | —— | Literal 已经在类型层挡住一半，运行期还要挡 |
| 年份超出 1900 ~ 2100 | —— | 防止把 `2026-02-17` 打成 `226-02-17` |
| `lead_days` / `aftermath_days` 越界 | —— | 负的提前量会让曲线反向 |
| `days_off` 内有重复日期 | `重复日期` | 打字错误的最常见形态 |
| 同一天既放假又补班 | `既放假又补班` | 逻辑矛盾，无法决定日型 |
| 锚点不在 `days_off` 里 | `不在放假区间` | 锚点是「正日子」，不放假的正日子说明数据错了 |
| 同一年两个节日共占一天 | `同时被` | 否则 `day_kind` 的答案取决于遍历顺序 |
| 同一 `(id, 年份)` 出现两次 | —— | 合并相邻年份时才会暴露 |

**为什么容忍缺失却不容忍错误**：缺一年的正确表现是「那一年不知道有什么节」——「不知道」是合法状态；而文件存在却读不出来意味着**有人写错了**，静默跳过的后果是那个节日凭空消失且毫无报错，比启动失败难查得多。

## 4. 强度曲线

### 4.1 定义

```
节前（days_until = gap，1 ≤ gap ≤ lead_days）：
    t = (lead_days - gap + 1) / (lead_days + 1)
    intensity = smoothstep(t) = t² · (3 - 2t)

节后（days_since = gap，1 ≤ gap ≤ aftermath_days）：
    t = 1 - gap / (aftermath_days + 1)
    intensity = smoothstep(t)

节日当天（含放假的每一天）：intensity = 1.0
```

选 smoothstep 而不是线性，是因为它在两端**导数为零**：曲线进入和离开节日时都是平滑的，不会在 `gap = lead_days` 那天突然开始爬。

`t` 的分子里那个 `+1` 是 R1 的关键：**外沿那天（`gap = lead_days`）的 `t` 不是 0，而是 `1 / (lead_days + 1)`**，所以强度大于 0——「提前 10 天就知道」这句话在数值上成立，而不是第 10 天还是 0、第 9 天才突然跳起来。

分母的 `+1` 是 R2 的关键：`gap = 1`（节前一天）时 `t = lead_days / (lead_days + 1) < 1`，所以**节前永远达不到 1.0**。D-1 和 D0 必须是两个不同的档，否则「过渡」退化成「切换」。

### 4.2 实测表（由 `_ramp_up` 跑出来，不是手算）

`lead_days = 4`（春节用的是 10，这里取短窗口以便看全）：

| 时点 | `gap` | `t` | `intensity` | 是否开始安排 |
| --- | --- | --- | --- | --- |
| D-4 | 4 | 0.20 | **0.1040** | 否 |
| D-3 | 3 | 0.40 | 0.3520 | **是** |
| D-2 | 2 | 0.60 | 0.6480 | 是 |
| D-1 | 1 | 0.80 | **0.8960** | 是 |
| D0 | 0 | —— | 1.0000 | 是 |

节后（`aftermath_days = 2`）：

| 时点 | `gap` | `t` | `intensity` |
| --- | --- | --- | --- |
| D+1 | 1 | 0.67 | 0.7407 |
| D+2 | 2 | 0.33 | **0.2593** |
| D+3 | —— | —— | 窗口结束，彻底安静 |

**每一个数字都不相同**，这一点有测试守着（`test_anticipation_intensity_rises_monotonically_and_differs_every_day`）。若哪天有人把 smoothstep 换成取整或分级，「曲线」会当场退化成「台阶」。

### 4.3 不同窗口长度的对照

`*` 表示已跨过安排阈值（见 § 5）：

```
lead=2 : D-1=0.741*  D-2=0.259
lead=4 : D-1=0.896*  D-2=0.648*  D-3=0.352*  D-4=0.104
lead=6 : D-1=0.945*  D-2=0.802*  D-3=0.606*  D-4=0.394*  D-5=0.198   D-6=0.055
lead=7 : D-1=0.957*  D-2=0.844*  D-3=0.684*  D-4=0.500*  D-5=0.316   D-6=0.156   D-7=0.043
lead=10: D-1=0.977*  D-2=0.913*  D-3=0.817*  D-4=0.699*  D-5=0.568*  D-6=0.432*  D-7=0.301  D-8=0.183  D-9=0.087  D-10=0.023
```

窗口越长，越靠外的几天强度越低——这正是想要的：春节「还有 10 天」和中秋「还有 2 天」给人的紧迫感本来就不同，而它们用的是同一条公式。

### 4.4 活动随强度解锁

`_take(activities, intensity)` 按强度取前 N 条准备活动：

```
count = round(intensity × len(activities))
```

特殊规则：若 `count == 0` 且 `intensity >= PREP_THRESHOLD`，则取 1 条。**这是为了不让「已经跨过阈值却还没排上任何事」出现**——阈值说过「开始安排了」，日程里却什么都没有，看起来像坏了。

于是春节（4 条准备活动、`lead_days = 10`）的表现是：

| 时点 | 强度 | 排上的准备活动 |
| --- | --- | --- |
| D-10 | 0.023 | —— |
| D-6 | 0.432 | 抢回家的票 |
| D-4 | 0.699 | 抢回家的票 · 买年货 |
| D-2 | 0.913 | 抢回家的票 · 买年货 · 收行李 |
| D-1 | 0.977 | 全部 4 条 |

`aftermath_activities` 同理按 `_ramp_down` 解锁——节后是**一条一条卸掉**，不是某天全部消失。

## 5. 两个时点：知道，与开始安排

`PREP_THRESHOLD = 0.35`。它把「节前」切成两段：

| 阶段 | 条件 | 表现 | 台词 |
| --- | --- | --- | --- |
| 知道 | `0 < intensity < 0.35` | 日程不变，但**知道**有这么回事 | 「过几天是中秋」（不主动提） |
| 开始安排 | `intensity >= 0.35` | 准备活动排进日程，会主动提起 | 「我已经在看回家的票了」 |

为什么要两个时点而不是一个：如果「提前 6 天」和「提前 1 天」的行为一样，那 R1 和 R2 就都退化成了「到点提醒」。而**「知道」和「开始安排」是两件不同的事**——人确实是先知道、过两天才动手的。这个阈值就是这个「过两天」的量化。

`HolidayContext.is_preparing` 是唯一的判断入口：

```python
@property
def is_preparing(self) -> bool:
    return self.phase == "anticipating" and self.intensity >= PREP_THRESHOLD
```

注意它同时看阶段和强度——只看强度的话，节后 0.74 的余温也会被误判成「在准备」。

## 6. 支配规则：今天归哪个节日

### 6.1 曾经的错误：按阶段排序

早期实现是「正在过 > 即将到来 > 刚过完」，理由是「不知道要过节比还没缓过来更要紧」。它在 2026-09-26 上错了：

| 节日 | 状态 | 强度 |
| --- | --- | --- |
| 中秋节（09-25，`aftermath_days = 1`） | 节后第 1 天 | **0.5000** |
| 国庆节（10-01，`lead_days = 7`） | 节前第 5 天 | 0.3164 |

按阶段排序，国庆会胜出，于是**中秋的「月饼还剩一堆」在第二天就被抹掉**，它立刻开始张罗国庆。这正是需求里点名要避免的「突然过渡」。而且它是静默的——`list` 和 `check` 都正常，只有 `today` 在特定日期少显示一行。

### 6.2 现在的规则

```
正在过（强度恒为 1.0）        ⇒ 直接胜出，无需特判
否则                          ⇒ 强度最大者胜出
平手时                        ⇒ 阶段序：过节 > 节前 > 节后
仍平手                        ⇒ 离今天更近者胜出
```

为什么这是对的：**强度本来就包含「离今天多远」的信息**。两个窗口重叠时，真正决定「今天是什么日子」的是哪个节日离得更近，而不是它排在哪个阶段。按强度比较，等于按远近比较——把两条特例规则合成了一条。

平手的处理保证**同一天同一份日历永远给同一个答案**（P6 可复现）：四元组排序键的后两段是确定的，所以 `max` 的结果唯一，不依赖 `holidays` 的迭代顺序。

### 6.3 交接是算出来的，不是特例

中秋与国庆的连续 15 天，全部由 `context()` 跑出：

| 日期 | 阶段 | 节日 | 强度 |
| --- | --- | --- | --- |
| 09-18 | —— | —— | 两条窗口都还没开始 |
| 09-19 | 节前 | 中秋节 | 0.0554 |
| 09-21 | 节前 | 中秋节 | 0.3936 |
| 09-22 | 节前 | 中秋节 | 0.6064 |
| 09-23 | 节前 | 中秋节 | 0.8017 |
| 09-24 | 节前 | 中秋节 | 0.9446 |
| 09-25 | 过节 | 中秋节 | 1.0000 |
| **09-26** | **节后** | **中秋节** | **0.5000** |
| 09-27 | 节前 | 国庆节 | 0.5000 |
| 09-28 | 节前 | 国庆节 | 0.6836 |
| 09-29 | 节前 | 国庆节 | 0.8438 |
| 09-30 | 节前 | 国庆节 | 0.9570 |
| 10-01 | 过节 | 国庆节 | 1.0000 |
| 10-04 | 节后 | 国庆节 | 0.8438 |
| 10-05 | 节后 | 国庆节 | 0.5000 |

**交接点在 0.5000 上对齐**：09-26 中秋以 0.50 压过国庆的 0.32；09-27 中秋的余温窗口结束，国庆升到 0.50 接手。没有空档，也没有重叠——因为两条曲线用的是同一个函数，只是斜率方向相反。

## 7. 日型：四值，不是两值

`day_kind(day)` 返回四个值之一，**优先级是 补班 > 放假 > 周末**：

| 日型 | 含义 | 界面文案 |
| --- | --- | --- |
| `makeup_workday` | 调休上班的周末 | 调休上班 |
| `holiday` | 落在 `days_off` 里的任意一天 | 放假 |
| `weekend` | 周六、周日 | 周末 |
| `workday` | 其余 | 工作日 |

**调休是朴素实现最容易漏掉的一格。** 「周末」看起来是 `weekday() >= 5` 就算，但调休把某个周六变成工作日、某个周三变成休息日。判错的后果很具体：调休上班那天它会睡到中午、发「今天休息」；而真正放假的那天它按工作日排满会议。

优先级顺序也不是随便定的——**补班必须排在放假前面**。理论上不会出现既放假又补班的一天（构造函数拒绝），但优先级写死之后，这两个判断就不依赖「构造函数确实拦住了」这个假设。

`day_kind` 与 `context()` 是两件事：前者回答「今天上不上班」，后者回答「今天像不像节日」。中秋节当天是 `holiday`；国庆节前的周六是 `weekend` 但 `context()` 会报节前强度 0.5。**两者都要**——只按日型排日程会漏掉「周末在为节日做准备」，只按节日强度会漏掉「这天本来是周末」。

## 8. 缺失与损坏的处理

三种情况的责任不同，所以处理方式也不同：

| 情况 | `load_year` | CLI | 理由 |
| --- | --- | --- | --- |
| 文件不存在 | 返回 `None`，记 `debug` | 退出码 2 + 人话 | 「不知道」是合法状态，不是错误 |
| 文件存在但解析失败 | 抛异常，带文件名 | 退出码 2 + 消息 | 有人写坏了，静默跳过会让节日凭空消失 |
| 年份越界（< 1900 或 > 2100） | 在 `path_for_year` 抛异常 | 退出码 2 + 「年份必须在」 | 路径都算不出来，这是个打字错误 |
| 日历不覆盖被问的那一年 | —— | 退出码 2 + 列出已有年份 | 见下 |

### 8.1 跨年视野，与它带来的陷阱

`load_calendar(year)` 读 `year - 1`、`year`、`year + 1` 三份并合并。原因很实在：**12 月 29 日要看的是 1 月 1 日**，不读相邻年份，年末那几天它就是瞎的。

但这个合并有个陷阱，实现时踩过：`load_calendar(2027)` 在磁盘上只有 `2026.toml` 时**照样返回一份日历**，只是它 `covers_year(2027)` 为假。若不拦住，`calendar list --year 2027` 就会拿 2026 的节日列表顶着 2027 的标题输出，退出码还是 0——**一个没人会发现的错答案**（和 § 6.1 的错法完全同类，都是「悄悄换掉答案」）。

现在的实现有两道闸：

1. `_resolve_calendar(year)` 在 `covers_year(year)` 为假时返回 `None`，调用方报「没有那一年的数据」。
2. `_cmd_list` / `_cmd_check` 再按 `holiday.day.year == year` 过滤一遍，避免合并进来的邻年节日混进列表。

第 2 条即使有了第 1 条也仍然必要：列表里混进一条 2027-01-01 的元旦而标题写着「2026 年节日」，是同一类错误的另一种形态。

### 8.2 `_require_year` 的报错文案

```
这份日历只有 [2026] 年的数据，回答不了 2027-05-01——
请补一份 holidays/<年份>.toml，不要拿相邻年份的调休安排硬套
```

后半句是给人看的**也是给未来的自己看的**：唯一的「快速修复」是把邻年的调休复制过来，而那会把错误的日期伪装成正确的。

## 9. 与作息模板的衔接

> ⚠️ **本节描述的是目标形态，尚未实现。** `schedule_template` 目前只有 `weekday:` / `weekend:` 两种日型（[DESIGN.md § 7.5](../DESIGN.md)），日程生成器本身也还没写。本节记录的是它应当如何接入。

`ScheduleBlock` 的 `category` 词表是 `("sleep","work","meal","commute","leisure","social","chore","other")`，**没有** `festival` 成员——这是刻意的，理由见 § 15.1。

目标形态是模板按**日型**给出多套日程，日型由节日上下文决定：

```yaml
schedule_template:
  weekday:        [...]
  weekend:        [...]
  pre_holiday:    [...]   # 节前，按 intensity 混合
  holiday:        [...]   # 放假日
  post_holiday:   [...]   # 节后，按 intensity 混合
```

混合规则：**不替换，而是按 `intensity` 加权**。强度 0.35 的周六不该变成一整套「准备过节」的日程，而应该是周末日程里插进一件事（去超市买月饼）。

```
最终日程 = (1 - intensity) × 基础日型日程 + intensity × 节日日程
```

若直接替换，强度从 0.34 跳到 0.35 那天日程会突变——**这又是同一个 bug 的第三种形态**。加权混合保证任何两天的日程差异都正比于强度差异。

`update_emotion` 与日程的另一条既有约束同样适用：日程块**只能由调用方（`TickContext`）查好后传进来**，纯函数不查时钟（[04](04-simulation-loop.md) § 6）。

## 10. 对话节奏：四条机制

四条都不会「像机器人」，但要反过来说——**人不是每条都秒回的**。这四条各自挡住一种非人感：

| 机制 | 挡住什么 | 实现 |
| --- | --- | --- |
| 打字延迟 | 每条都瞬间回复 | `INSTANT_LOW_S = 1.5` ~ `LOW/HIGH` 分档 |
| 睡觉/开会不回 | 凌晨三点秒回 | 复用 `ScheduleBlock.interruptible` |
| 不会一直被动应答 | 只会一问一答 | `PASSIVE_TURNS_BEFORE_TOPIC = 4` |
| 不复读自己 | 同一句话反复说 | 二元组 Jaccard 相似度 |

### 10.1 决策链

`decide_reply()` 是纯函数，六条短路规则按优先级排列：

| 序 | 条件 | 结果 | 理由 |
| --- | --- | --- | --- |
| 1 | 当前日程块不可打断 | `much_later` | 睡觉、开会、通勤中——**这是唯一的硬约束** |
| 2 | `fatigue >= 0.95` | `silent` | 累到不想说话 |
| 3 | `fatigue >= 0.85 或 valence <= -0.5` | `delayed` | 累或低落 → 慢半拍 |
| 4 | `consecutive_instant >= 3` | `normal` | 连着秒回三条，第四条必须慢下来 |
| 5 | `text_length <= 6` | `instant` | 短消息可以快回 |
| 6 | 其余 | `normal` | —— |

**为什么顺序不能换**：第 1 条在睡觉这一格上，比「累」「低落」「消息短」都更硬——不可打断的日程块里发消息，是把「它在开会」演成笑话。第 4 条必须在第 5 条前面：先看历史连击，再看这条多短，否则短消息永远秒回，连击规则就永远不会触发。

延迟是**区间加抖动的乘法**，不是固定值：`_jitter(low, high, roll)`。固定值会让三条消息的延迟都一模一样——那也是非人感。

### 10.2 主动开话题

`should_open_topic()` 的硬门槛全部否决后，概率是：

```
chance = min(0.2 + 0.15 × extra_passive_turns + max(valence, 0.0) × 0.3, 0.95)
```

三个设计选择：

- **被动轮次越多越可能主动**（`+0.15`/轮）：一直被动应答本身就是非人感，所以它是**推**主动性的信号。
- **心情好才主动**（`valence > 0` 才有 `+0.3`）：负面情绪不影响「会不会主动」，这比「心情差就不理人」更接近真人。
- **封顶 0.95 不是 1.0**：留一点不确定性。概率 1.0 意味着「聊了 N 轮之后必然主动」，那又成了定时任务。

`TOPIC_COOLDOWN_MINUTES = 30` 防止刚换完话题又换。测试断言的是 reason 里出现具体原因（`先顺着`、`别一直换话题`、被阻挡的活动名、`PASSIVE_TURNS_BEFORE_TOPIC` 的数字），所以**每一条否决都必须写清楚为什么**——否则日志里只剩一个 `False`。

### 10.3 为什么这些是「机制」不是「提示词」

对照 P3。每条准则都有对应的**代码分支**，而且每一条都有测试：

| 口头准则 | 若只写在提示词里的失效方式 |
| --- | --- |
| 「不要秒回」 | LLM 有时会，有时不会，无法复现 |
| 「睡觉的时候别回」 | 需要 LLM 自己知道现在是几点，且真的照做 |
| 「不要一直被动」 | 每轮都重新决定，可能连续 20 轮不主动 |
| 「别重复」 | LLM 不知道自己三小时前说过什么 |

## 11. 不复读自己

`REPETITION_THRESHOLD = 0.6`，用**字符二元组集合的 Jaccard 相似度**：

```
similarity(a, b) = |bigrams(a) ∩ bigrams(b)| / |bigrams(a) ∪ bigrams(b)|
```

选二元组而不是分词，是因为中文没有空格、`jieba` 又在可选 extras 里（P5：不能为一个小功能引依赖）。二元组对中文短句的粒度刚好——比单字更能抵抗正常换词，比整句更能抓住「差不多的意思」。

### 11.1 一个真实的 bug：标点必须先去掉

实现时先用 `bigrams` 直接跑，结果**最该抓到的那类复读一个都没抓到**：

| 比较 | 去标点前 | 去标点后 |
| --- | --- | --- |
| 「好嘞~」 vs 「好嘞！」 | 0.33 | **1.00** |
| 「嗯嗯」 vs 「嗯嗯嗯」 | —— | —— |

原因：中文短句里标点占的比重大得离谱。四个字符的句子里两个是标点，相似度被稀释到 0.33，正好落在阈值 0.6 以下——恰恰漏掉最常见的口头禅复读。

修法是过滤掉 Unicode 分类里的 `P*`（标点）与 `S*`（符号，含 emoji 与 `~`）：

```python
def _is_noise(char: str) -> bool:
    return char.isspace() or unicodedata.category(char)[0] in {"P", "S"}
```

**这里的教训是通用的**：任何对中文文本做的字符级统计，都先问一句「标点算不算」。算进去通常不是想要的结果。

## 12. 可复现性契约

`decide_reply()` 与 `should_open_topic()` 都**不自己取随机数**，而是接收一个 `roll: float`：

```python
decide_reply(*, now, block, emotion, text_length, consecutive_instant, roll)
```

调用方从 `ctx.rng.random()` 取（P6）。三个直接好处：

| 好处 | 具体表现 |
| --- | --- |
| 决策链可测 | 传 `roll=0.99` 就能确定性地走到某个分支，不用 mock |
| 能重放 | 同一个 `random_seed` 跑同一段时间，消息时机完全一致 |
| 推迟取随机数 | 短路分支（如睡觉）根本不消耗随机数，随机流的消耗只取决于实际走了哪些分支 |

第三条常被忽略但很重要：如果每个函数开头都先 `roll = rng.random()`，那么走不同分支的两次运行会消耗不同数量的随机数，后续所有决策全部错位，重放失效。

红线 3 有一条检查专门挡这个：`sim/` 里不得 `import random`。`domain/` 是纯函数层，连 `import random` 的机会都不给它——随机值只能从参数进来。

## 14. 界面

### 14.1 CLI

```
alterego calendar list [--year 2026]          一年的节日一览
alterego calendar today [--date 2026-09-26] [--days 14]
alterego calendar check [--year 2026]         数据可信度：哪些日期还没核对
```

退出码：`0` 正常 / `2` 数据缺失或年份越界（配置类错误，不是崩溃）。`--year` 与 `--date` 默认按**内核时区**算「今天」，不是进程本地时区——见 § 14.2。

### 14.2 「今天」必须按内核时区算

`cli.py` 不写 `date.today()`，而是：

```python
zone = resolve_timezone(Config.load().core.timezone)
return datetime.now(zone).date()
```

`date.today()` 按进程本地时区算。若容器装的时区是 UTC，东八区早上 8 点之前 UTC 还停在昨天——而节日问的就是「哪一天」，**差一天就是差一个节日**（跨年时甚至差一年）。ruff 的 `DTZ011` 正是拦这个。

### 14.3 中文表格要按显示宽度对齐

`alterego calendar list` 是一张表，第一版用 `f"{text:<8}"` 排版，结果是所有含中文的列错位——因为 `str.ljust` 数的是**字符个数**，而中文一个字占**两列**。

修法是按 `unicodedata.east_asian_width()` 算真实宽度，`_pad()` 补差额。这条经验值得单独记：**任何终端里输出 CJK 表格的地方都会踩它**，而且看起来只是「有点歪」，不会报错。

### 14.4 样例输出

```
$ alterego calendar today --date 2026-09-26
2026-09-26  周六  周末
──────────────────────────────────────────────────────────
节后 中秋节（1 天前）  强度 █████░░░░░ 0.50
  这段时间大概会：月饼还剩一堆

未来 14 天
  10-01  周四  国庆节  5 天后 · 放假 3 天（10-01 ~ 10-03）
```

同一个 09-26，在 § 6.1 的错误规则下第一段会写成「节前 国庆节（5 天后）强度 0.32」——**中秋不见了**。这就是那条回归测试守的东西。

```
$ alterego calendar today --date 2026-09-19
2026-09-19  周六  周末
──────────────────────────────────────────────────────────
节前 中秋节（6 天后）  强度 █░░░░░░░░░ 0.06
  → 还只是知道（跨过 0.35 才排进日程）

未来 14 天
  09-25  周五  中秋节  6 天后 · 放假 09-25
  10-01  周四  国庆节  12 天后 · 放假 3 天（10-01 ~ 10-03）
```

R1 与 R2 在这一屏上都能直接看到：**知道**（0.06）但还没**安排**（提示里写明「跨过 0.35 才排进日程」）。

### 14.5 两个展示层的坑（`_span` 与 `_pad` 之外）

`_span(holiday)` 先看 `days_off` 再看 `length_days`：

```python
if not holiday.days_off:
    return "不放假"
```

原因：`Holiday.span` 在 `days_off` 为空时**退化成 `(self.day,)`**，这是为了让 `covers()` 能工作。情人节、元宵节、圣诞节的锚点因此落在 `span` 里，但它们不放假——只按 `length_days <= 1` 判断会把它们写成「放假 02-14」。**领域层的兜底值不是数据**，展示层不能当数据用。

`_cmd_today` 在「未来 N 天」为空时也打印标题和「这几天没有节日」，而不是整段消失——整段消失会让人以为 `--days` 没生效。

## 15. 边界与不做

### 15.1 不给 `ScheduleCategory` 加 `festival`

看起来自然，但会同时牵动三处：

1. `domain/schedule.py` 的 `SCHEDULE_CATEGORIES` Literal；
2. `001_initial.sql` 里 `schedule_block.category` 的 CHECK 约束；
3. [03-data-model.md](03-data-model.md) § 4.2 的枚举值汇总表。

按 [AGENTS.md](../../AGENTS.md) § 9，改这三处要先改文档或写 ADR。**本批次刻意不加**：日程生成器还没写（§ 9），现在加进去的是一个没人用的枚举成员，而删掉它比加上它麻烦。等 § 9 落地时一并处理。

### 15.2 不做农历推算

`2026.toml` 里农历节日的日期是**查表写死的**，不是算出来的。理由：农历与节气需要天文历法实现，误差一天就等于过错节；而这张表一年更新一次，成本远低于写一个「基本正确」的历法（`verified = false` 标出哪些还没核对，这是诚实的成本）。

### 15.3 不做「节日倒计时」这类主动播报

`intensity` 是给日程与提示词用的**内部量**，不是给用户看的倒计时。强度 0.35 不意味着「该发消息说 6 天后的中秋」——主动提起的时机由 § 10.2 的 `should_open_topic()` 决定，而它与强度是两条独立的通路。

### 15.4 不做节日相关的生图

形象一致性见 [07](07-model-routing-and-media.md)，与节日无关。若将来要做「节日自拍」，走的是 `image` 插件的现有契约，`calendar.py` 不需要知道这件事。
