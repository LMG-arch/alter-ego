## 2. 顺序：为什么是「预算 → 意图 → 阶段 → 引擎 → 会话 → CLI/Web」

依赖是单向的，倒过来写任何一步都会写出没有调用方的死代码：

```
budget.py      纯函数，无依赖           ← 先写，因为它是 P3「机制约束」的落地点
intents/       纯数据，依赖 interfaces.IntentType
stages/        依赖 budget + intents + TickContext.llm()
engine.py      依赖 stages + repository
conversation.py 依赖 domain.conversation（已实现）+ gateway（已实现）+ repository
cli_chat.py    依赖 conversation + 组装根
channels/web/  依赖 conversation（对话页）+ settings（设置页）
```

**先做对话主体，因为它是最上面那块，也是最缺的。** 设置与插件加载都是「把已有的能力
露出一个入口」，一天之内能做完；Web UI 则要等对话路径存在才有页面可写。

## 3. 四条硬性约束（这次每一块都要过）

从 `docs/DESIGN.md` § 3 与 `scripts/check_architecture.sh` 的 23 项里挑出与本计划相关的：

| 约束 | 落在哪 |
| --- | --- |
| `sim/` 不得用 `datetime.now()` / `time.time()`（红线 15） | 引擎与阶段一律走 `ctx.virtual_now` |

| 单文件 ≤ 900 行（红线 23） | `kernel/config.py` **已经是 900/900**，设置中心的任何新配置段必须开卫星模块 |

### 批次 A · 对话主体

| 文件 | 内容 |
| --- | --- |
| `sim/budget.py` | `BudgetUsage` / `BudgetDecision` / `check_budget()` / `record_sent()` / `record_no_reply()`，**纯函数**。五条有序检查按 `04-simulation-loop.md` § 5 的 940–1012 行 |
| `sim/intents.py` | 11 种内置意图的 `IntentType` 目录 + `select_candidates()` |
| `sim/stages/{sense,reflect,intention,act,express,persist}.py` | 六个阶段，`order` 10/30/50/70/90/110 |
| `sim/engine.py` | `SimulationEngine.tick()`：`on_tick_pre` → 六阶段 → `on_tick_post` → 合并 → 落库 → `tick.completed` |
| `sim/conversation.py` | `ConversationService.reply()`：入站消息 → 落库 → 组提示词 → 调模型 → 落库 → `OutboundMessage` |
| `sim/context.py` | 补 `TickContext.llm()`（走 `ServiceRegistry` 取 `LLMGateway`） |
| `interfaces/repository.py` | 新增 `ConversationRepository` / `BudgetRepository` / `ActivityLogRepository` / `TickLogRepository` 四个 Protocol |
| `storage/sqlite/repositories.py` | 上述四个的 SQLite 实现 |
| `cli_chat.py` | `alterego chat`（`--once` 单句、`--show-prompt` 看组出来的提示词） |
| `domain/__init__.py` | 若新增领域模块要登记 |

**为什么会话不走 tick 而要单独一条路径。** `04-simulation-loop.md` § 3.3 说 `reply` 意图
在有未读消息时权重 1.0，那是**主动行为的调度**；而用户在 Web 上打完字等回复，等不了一个
tick（`realtime` 模式 5 虚拟分钟 ≈ 5 分钟）。两条路径共用同一套纯函数
（`domain.conversation.decide_reply` 决定即时/正常/延迟），但触发时机不同：
**tick 决定「它想不想主动找你」，会话路径决定「你说了话它怎么回」。**

## 5. 这次明确**不做**的事

写下来是为了下一次不用重新推一遍：

| 不做 | 为什么 |
| --- | --- |
| 真实 IM 渠道（企业微信 / 钉钉 / Telegram）发出站之外的实现 | ADR-0004 已定 v1 只做出站；`wecom` 依赖外置在 optional extra |
| NPC 之间的对话（`npc/` 目前是空壳） | `04-simulation-loop.md` 有规定，但它不阻塞「主体」四块；留给下一轮 |
| `image` / `source` 两大类插件的**具体实现**（生图供应商、RSS 抓取器） | 本批次只把**契约与扩展点**补齐（审计第 1、2 项），实现是后续插件的事 |
| 打字延迟的真实 `asyncio.sleep` | `decide_reply` 已经算出延迟值；真睡着会让测试变慢、让 SSE 页面看起来卡住。先把值算出来、展示出来、落库，睡眠交给渠道 |
| 设置页的「立即重启」按钮 | 需要进程管理器，属于运维范畴；页面只显示「有 N 项需重启」 |
