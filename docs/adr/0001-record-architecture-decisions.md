# ADR-0001 · 采用架构决策记录（ADR）机制

- **状态**：已接受
- **日期**：2026-09-15
- **决策者**：LMG-arch
- **相关**：[`docs/DESIGN.md`](../DESIGN.md) § 14 版本管理与文档纪律
- **影响范围**：全体（流程约定）

---

## 背景

本项目是一个长期演进的个人项目，有几个特点使"记录决策理由"变得格外重要：

1. **设计文档很详细。** `docs/DESIGN.md` 加七个分册覆盖了架构、插件、数据、推演、渠道、路线图。文档说明了**系统现在长什么样**。

2. **但文档不记录"为什么不是另一个样子"。** 例如：
   - 为什么内核用 `Clock` 协议而不是直接 `datetime.now()`？
   - 为什么 `reach_out` 被拦截时是降级而不是丢弃？
   - 为什么 v1 的钉钉渠道只能发不能收？

   这些决策的**约束条件**（"Go 的插件在 Windows 上不可用"、"用户可能误解单向渠道"）散落在对话、思考和临时笔记里，没有落到文件。

3. **开发周期长。** 按 `06-roadmap.md` 的估算约 35–45 人日，且 F 阶段（推演引擎）需要反复调试。中间必然会有中断与重启。

4. **实际风险已经出现过。** 设计过程中至少两次差点选错语言（倾向 Go/Rust 因为"快、省内存"），如果当时没有把"插件式开发是硬性需求"这个约束写下来，几周后很可能又走一遍同样的弯路。

需要一个机制，记录**决策 + 约束 + 代价**。

---

## 决策

采用 **ADR（Architecture Decision Record）** 机制：

1. 所有重大架构决策必须写成 ADR，存放在 `docs/adr/`。
2. 文件命名 `NNNN-<短横线描述>.md`，编号从 `0001` 连续递增，`0000` 保留给模板。
3. ADR 一旦「已接受」**正文不可修改**。改变决策需写新 ADR，并更新旧 ADR 的**状态行**。
4. 判断标准：**做错了需要超过一天返工成本的决策**。不确定时写了不亏。
5. 每个 ADR 必须包含：背景（约束）/ 决策 / 考虑过的方案 / 副作用（含负面）/ 对设计原则的影响 / 需同步的文档 / 验证方式。
6. 写 ADR 时必须同步更新对应设计文档。冲突时以设计文档为准，先改文档。

维护索引表在 `docs/adr/README.md`。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 是否采用 |
| --- | --- | --- | --- |
| **ADR 独立文件** | 有完整历史；git blame 友好；可被单独引用；社区通用格式 | 文件数量会增长 | ✅ |
| 在 `DESIGN.md` 里加「决策记录」章节 | 不用新目录 | 文档会膨胀到不可读；历史与现状混在一起；无法标记状态流转 | ❌ |
| 写在代码注释里 | 贴近实现 | 跨模块决策无处安放；重构代码时容易丢；非开发者看不到 | ❌ |
| 用 GitHub Issues / Discussions | 无需维护文件 | 与代码脱节；仓库克隆后看不到；会被 issue 淹没 | ❌ |
| 用 PR 描述 | 天然关联变更 | PR 会被合并、难以检索；不构成"决策清单" | ❌ |
| 不记录，靠记忆 | 零成本 | 已经验证过：三次差点重复选错语言 | ❌ |

### 为什么否掉「写在设计文档里」

这是最初倾向的方案——少一个目录，所有内容在一处。

放弃的原因是**两者的生命周期语义不同**：

- 设计文档描述**当前状态**，应当随时更新到最新
- ADR 描述**某个时刻的判断**，应当永久冻结

混在一起会导致两种失败：要么设计文档里堆满历史（读不下去），要么历史被不断覆盖（等于没写）。分开后，设计文档回答"是什么"，ADR 回答"为什么"，各自可以做到最好。

### 为什么否掉「靠记忆」

这一条是实际经验，不是理论担忧。

设计初期用户明确要求"选择加载快、内存占用少、代码简单的语言"——这个描述指向 Go 或 Rust。如果只按这句话选，就会选 Go。但 Go 的 `plugin` 包**在 Windows 上官方不支持**，而用户的硬性需求是"插件式开发，后续好添加功能"，且用户环境是 Windows。

结论（Python）与用户第一句话的字面意思**相反**。如果不把"插件式热加载是硬性需求 + 环境是 Windows"这两个约束写下来，将来任何人（包括自己）看到 `docs/design/01-architecture.md` 里用 Python 时，都可能想"这么慢的语言，为什么不换掉"，然后重蹈覆辙。

## 后果

### 正面

- **约束被固化。** 决策的理由写在文件里，不依赖记忆。
- **否决记录同样有价值。** 「已拒绝」状态的 ADR 防止同一个想法被反复讨论。
- **新贡献者（或未来的自己）能理解奇怪的设计。** 看到 `kernel/clock.py` 里的 `Clock` 协议时，能找到 ADR 解释为什么不用 `datetime.now()`。
- **改变决策有明确的路径。** 不是"直接改代码"，而是"写 ADR → 更新文档 → 改代码"。
- **与 CI 形成闭环。** 架构红线（`scripts/check_architecture.sh`）检测"违反了规则"，ADR 记录"为什么这么定规则"。两者互补：红线说不许越界，ADR 解释边界画在哪里以及为什么。

### 负面

- **额外维护成本。** 每个重大决策约需 20–40 分钟撰写。按 35–45 人日的总工作量估算，预计产生 15–25 个 ADR，累计 6–15 小时。
- **索引容易忘记更新。** `docs/adr/README.md` 的表格需要手动维护，存在遗漏风险。
- **有过早写 ADR 的诱惑。** 可能把"改个函数名"也写成 ADR，产生噪音。
- **对个人项目来说略显仪式化。** 单人项目通常不需要这么正式。

### 需要关注

- **如果 ADR 开始变成复述设计文档**，说明判断标准松了，需要收紧到"做错要返工一天以上"。
- **如果连续很多次改动都没有 ADR**，说明要么项目已经稳定（好事），要么判断标准紧了，需要检查。
- **如果索引表超过 30 行**，考虑按状态或主题拆分。

## 对设计原则的影响

| 原则 | 影响 |
| --- | --- |
| P1 内核无知 | 无影响（但 ADR 是记录"为什么内核要无知"的地方）|
| P2 显式优于隐式 | **支持**。决策理由显式写出来，而不是隐式留在作者脑子里 |
| P3 机制约束优于提示词祈祷 | 无影响 |
| P4 可插拔优于可配置 | 无影响 |
| P5 标准库优先 | 无影响（ADR 是纯 Markdown，无依赖）|
| P6 可复现 | **支持**。同样的约束下能得到同样的结论 |
| P7 文档与代码同生共死 | **支持**。ADR 是文档纪律的一部分（见 `CONTRIBUTING.md § 文档纪律`）|

## 验证方式

ADR 机制本身无法自动化验证，但可以用以下方式定期自检：

| 检查 | 方式 | 频率 |
| --- | --- | --- |
| 新决策是否有 ADR | PR 模板中「架构红线」必填项 | 每次 PR |
| 索引是否完整 | 对比 `docs/adr/*.md` 与 `README.md` 表格行数 | 每月 / 发布前 |
| ADR 是否与设计文档一致 | 检查每个"已接受" ADR 的文档同步 checklist 是否勾满 | 发布前 |
| 是否有该写未写的决策 | 回顾 git log 中 `arch` 与 `!` 标记的提交，确认都有对应 ADR | 每阶段结束 |

**判断机制是否有效的关键指标**：未来半年内，是否出现过"重复讨论一个已被 ADR 否决的方案"。如果出现过，说明 ADR 没有被读到——那问题在于可发现性，需要考虑在 `CONTRIBUTING.md` 和 PR 模板中更醒目地引导。
