# ADR-0013 · 插件读不到的值，由宿主在合适的时机广播给它

- **状态**：已接受
- **实施状态**：已实现（`cli_serve.SERVE_LISTENING` + `plugins/desktop_window/`）
- **日期**：2026-09-16
- **决策者**：LMG-arch

  [ADR-0012](0012-specialized-study-is-a-curriculum-not-a-prompt.md)、
  [`docs/guide/plugin-development.md`](../guide/plugin-development.md) § 2.4.1 / § 2.4.2、

- **影响范围**：`kernel/plugin.py`（无改动）、`kernel/bus.py`（无改动）、
  `cli_serve.py`（新增一条广播）、`plugins/desktop_window/`

## 背景

插件能 import 的只有两处：`alterego.interfaces.*` 与 `alterego.kernel.plugin`
（`tests/test_interfaces_consistency.py` 守着这条）。这不是疏漏，是 P1 的直接后果：
**内核无知，插件也无知**——插件不该知道 Web 层用什么框架，不该看见 `Config` 的
全部字段（里面有 `auth_password` 这类密钥），更不该去碰已经装好的存储连接。

于是出现一种以前没遇到过的需求：**插件需要某一个值，而它按规则根本读不到。**

具体的例子是桌面窗口插件（`capability.desktop_window`）。它的作用是拿浏览器开一个
指向本机 Web 界面的窗口，所以它必须知道界面在哪个地址上。而地址是
`[web] host` / `[web] port` 算出来的，读它们的是 `cli_serve`：

- 插件**不能**在自己的 `[plugin.config.*]` 里再声明一份 port/url。
  那是同一件事的两个真源——用户改 `[web] port` 之后窗口还开在旧端口上，
  两个地方都「看起来对」，其中一个是谎话。
- 插件**不能** `import alterego.kernel.config` 或 `import alterego.cli_serve`。
  前者会把整份配置（含密钥）交到插件手里，后者会把 Web 层的内建实现
  焊进插件——换一个 Web 渠道插件就崩。
- 插件**不能**自己猜。写死 `127.0.0.1:8765` 会在用户改端口时**静默**失效，
  而这类「没报错、也没反应」的故障最难查。

值本身也不该原样交出去：`0.0.0.0` 是「听所有网卡」，不是一个能打开的地址；
`::` 同理。**插件要的是算好的结果，不是原料。**

## 决策

**宿主把插件读不到、又必须知道的值，在它真的成立的那一刻，作为事件广播出去；
插件订阅那条主题。**

具体到这次的实现：

```python
# cli_serve.py
#: 界面真的开始在某个地址上监听之后，广播的主题。
SERVE_LISTENING: Final[str] = "serve.listening"
# 载荷：{"url": str, "port": int}
```

```python
# plugins/desktop_window/plugin.py
def on_event(self, event: Any) -> None:
    if getattr(event, "topic", "") != SERVE_LISTENING:
        return
    ...
```

配套五条硬要求（写进指南 § 2.4.2，作为以后所有这类缝的验收标准）：

1. **广播方是唯一算那个值的地方。** 这里是 `cli_serve._url()`——它把
   `0.0.0.0` / `::` 改写成能打开的地址，是仓库里唯一做这件事的实现。
2. **发在「那个东西真的存在之后」，不是「进程起来之后」。** 这条广播要等
   uvicorn 自己报 `started` 才发；端口被占了则**一条都不发**。
3. **载荷里不放凭据。** 事件的去向是每一个订阅者**加事件日志**，token 进去
   就等于公开。
4. **插件侧第一行先判主题。** `on_event` 收到所有事件（内核是按 `"*"` 订阅的），
   不判就是每个 tick 白跑一遍。
5. **名字要用一条测试把两边钉住。** 插件够不着 `cli_serve` 的常量，只能各写一份
   字面量；对不上时**一句话都不报**，症状是「界面起来了但快捷键永远没反应」。

## 后果

### 正面

- **插件保持无知。** 它不知道 Web 用什么框架、不知道配置有几层、不知道
  `0.0.0.0` 的语义——它只知道「界面在这儿了」。
- **广播天然带着时机。** 这是事件相对「让插件读配置」最大的优势：配置是**状态**，
  任何时刻读都有值（也许是错的）；事件是**事实**，只在它成立的那一刻才有。
  桌面窗口插件要的正是这个——`alterego plugins doctor` 也走 `load_all()`，
  而它不该占掉用户的全局快捷键。如果插件是从配置里读地址的，doctor 就无从知道
  「界面还没起来」。
- **订阅者数量对宿主透明。** 以后多一个插件想知道界面地址，`cli_serve` 一行都不用改
  （P4）。
- **不需要新 API。** `PluginContext` 还是 11 个字段 5 个方法，
  `ctx.provide()` 那条被否掉的路（见 [13](../design/13-interface-consistency.md) § 2）
  依旧不需要开。

### 负面

- **多了一层只靠约定维持的间接。** 编译器和类型检查都帮不上忙：主题名是一段字符串，
  载荷是 `Mapping[str, Any]`。第五条第要求（一条测试钉住常量）就是在补这个洞，
  但它补得住名字、补不住载荷结构。
- **广播没有重放。** 在广播之后才加载的插件收不到。今天的实例不受影响
  （广播只发生在 `serve` 启动时，而插件在 `serve` 启动时加载），
  但这是一个**只靠时序成立**的性质，不是设计保证的。
- **`event_log` 默认关闭**，所以这条广播不会留下审计记录。查「为什么窗口没开出来」
  时会缺一条线索，只能看插件自己的日志。
- **它会给插件作者一种「什么都能问宿主」的错觉。** 实际上只有宿主**主动**
  想到要广播的东西才拿得到。拿不到的东西就是拿不到，不存在「再试一个 API」这条路。

### 需要关注

- **载荷变了要当成破坏性变更**处理：加字段要同时在插件侧给默认值，
  改字段名要当作 `api_version` 那一类的事来看。
- **如果哪天需要「广播之后才加载的插件也拿得到」**，就得引入一个
  「最后已知值」的缓存（`ctx.state` 或内核侧），或者给插件一个主动查询的口子。
  那时要重新评估——因为那等于把「事件」又变回了「状态」，
  而这次选事件的理由正是它带时机。
- **别把这条缝当成搬配置项的通道。** 如果某个值只是「插件想改它」，
  那它是设置项的事（[ADR-0010](0010-every-setting-carries-display-metadata.md)）；
  如果某个值「别人已经读了，插件只是知道有这回事」，那它连广播都不需要。

## 备选方案

| 方案 | 优点 | 缺点 | 是否采用 |
| --- | --- | --- | --- |
| A · 插件在 `[plugin.config.*]` 里再声明一份 port/url | 零新机制，符合现有清单能力 | 同一件事两个真源，改 `[web]` 不改插件，两边都「看起来对」 | ❌ |
| B · 放宽 import 白名单，让插件读 `kernel.config` | 实现最短 | 插件拿到整份配置（含 `auth_password`）；P1 与插件隔离一起破 | ❌ |
| C · `ctx` 新增 `ctx.require_value("web.port")` 之类的方法 | 插件可以按需取 | 等于给插件一个读任意配置项的口子；而且**给的是原料不是结果**，`0.0.0.0` 还是得插件自己处理——于是每个插件各改一遍 | ❌ |
| D · 宿主广播事件，插件订阅 | 插件保持无知；天然带时机；订阅者数量对宿主透明；不需要新 API | 多一层约定，类型检查帮不上忙；没有重放 | ✅ |
| E · 插件自己猜（默认 `127.0.0.1:8765`） | 零成本 | 用户改一个端口就**静默**失效 | ❌ |

### 为什么否掉其他方案

**A 最能说明问题**，因为它「看起来最像我们已经有的东西」。清单配置项是给
「只有你的插件读的旋钮」用的；而 port 不是旋钮，是**事实**。把它抄进插件里，
改 `[web] port` 不会改窗口的地址——而用户会以为改了。这比直接报错更坏。

**B 与 C 是同一个错误的两面**：都试图把「插件读不到」这件事当成一个**能力缺口**
去补，而它其实是一条**设计边界**。B 干脆拆掉边界；C 在边界上开一个洞，
而且开的还是错的那个洞（给原料不给结果）。C 还有一个更隐蔽的代价：
`0.0.0.0` / `::` 的改写逻辑会从一处变成每用到的插件各一处，
而真实的地址格式只有 `cli_serve._url()` 知道（它为此有 3 条断言）。

**E 的失败模式最难查**：没有异常、没有日志、没有提示，界面正常跑在 8080 上，
而快捷键开出来的窗口对着 8765 白屏。**一个静默失效的方案比一个会报错的方案坏得多。**

## 依据

- 指南 [`plugin-development.md`](../guide/plugin-development.md) § 2.4.1
  的决策表第三行：**「内核或某条命令已经读它，你的插件只是『知道有这回事』」→
  不要搬过来。** 本节是那一行的另一半：不搬过来之后，插件怎么知道？
- [`13-interface-consistency.md`](../design/13-interface-consistency.md) § 2 否掉 `ctx.provide()`
  的理由（薄封装会让插件作者以为「什么都能要到」），这里沿用同一条判断。
- [`05-channels.md`](../design/05-channels.md) § 7.4：「窗口是浏览器开出来的，
  不是自己画的」——正因为它开的是一个真实的 Web UI，地址这件事才**必须**是同一份。
- `tests/test_desktop_window_plugin.py::TestConsistencyWithTheAssemblyRoot`
  是最低限度的机械保证：它断言插件的 `SERVE_LISTENING` 等于 `cli_serve` 的，
  并且 `_announce_listening` 的载荷里**没有** `token`。

## 对设计原则的影响

| 原则 | 影响 |
| --- | --- |
| P1 内核无知 | **支持**。插件不需要知道 Web 层怎么实现，宿主也不需要知道有谁在听 |
| P2 显式优于隐式 | **部分冲突，已用测试与注释补偿**。事件总线上的广播是隐式的——宿主发出去不知道谁在听，插件收得到也看不见发的人。补偿手段是「两边各留一句指向对方的注释」＋「一条钉住常量的测试」 |
| P3 机制约束优于提示词祈祷 | **支持**。「端口被占了就不广播」是代码行为，不是一句「请不要在端口冲突时开窗口」 |
| P4 可插拔优于可配置 | **支持**。宿主不认识订阅者，多一个订阅者零改动 |
| P5 标准库优先 | **无影响**。这条缝用的事件总线本来就在 |
| P6 可复现 | **无影响**。这条广播不参与推演循环，不影响可复现性 |
| P7 文档与代码同生共死 | **支持**。五条硬要求与这条决策一起落进指南 § 2.4.2 与 ADR |
