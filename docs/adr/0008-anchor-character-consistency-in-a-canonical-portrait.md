# ADR-0008 · 角色形象一致性锚定在一张定妆照上

- **状态**：已接受
- **日期**：2026-09-15
- **决策者**：LMG-arch
- **相关**：[docs/design/07-model-routing-and-media.md § 5](../design/07-model-routing-and-media.md#5-角色一致性机制而非提示词)、[ADR-0006](0006-ship-implementation-choices-as-data.md)
- **影响范围**：`domain/media.py`、`interfaces/image.py`、`capability.selfie`、新表 `media_asset`

---

## 背景

角色需要能生成自己的图片（自拍照、风景照、生活场景照），并且**形象前后一致**——同一个人，
只换衣服与所处环境。

这个需求有一个不明显的困难：**扩散模型每次生成都从随机噪声出发。**
同一个提示词生成一千次，得到一千个不同的人。而「同一个人」这件事，无法通过把形容词写得更详细来解决——
「25 岁、短发、圆脸、眼睛稍大」不足以固定一张具体的脸，模型每次翻译这段文字都会得到不同的结果。

于是问题变成：**「这个人是谁」要放在哪里，模型才能每次都看到同一个答案？**

有三个候选位置：

1. 提示词里（文字描述长相）
2. 随机种子里（固定 seed）
3. 参考图里（把一张已有的脸喂给模型）

以及第四个选项：**训练一个 LoRA**（把角色烘焙进模型权重）。

## 决策

我们采用 **「定妆照（canonical portrait）」作为角色形象的唯一真源**，并把它固化为一套**三层机制**，
全部由代码强制，而非由提示词建议：

1. **定妆照**：建人设时生成且仅生成一张正面、中性表情、纯色背景的形象照，连同**生成它的完整参数**
   （prompt / seed / model / provider）一起存入 `media_asset`，`role = 'canonical'`，
   由数据库部分唯一索引保证全库只有一张。同时存一段人工可编辑的 `appearance_brief` 文字描述。
2. **参考图传递**：每次生图都必须把定妆照放入 `ImageRequest.reference`。
   `supports_reference = false` 的供应商**被拒绝生成人物图**，只允许生成风景与物品。
3. **固定骨架 + 四槽位**：提示词由一个不可变的骨架（长相描述来自 `appearance_brief`）
   加上恰好四个可变槽位（`outfit` / `scene` / `mood` / `lighting`）组成。
   骨架的构造函数是 `domain/` 里的纯函数 `build_portrait_prompt()`，**没有第二个入口**。

并接受一个明确的量化验收标准：

> 同一份定妆照，生成 20 张不同场景的图，人眼判断「是同一个人」≥ **16/20（80%）**。

达不到则更换 provider，或启用 § 备选方案 D（LoRA）。这条判定人工做一次并记录结论。

## 考虑过的方案

| 方案 | 优点 | 缺点 | 是否采用 |
| --- | --- | --- | --- |
| A · 只靠提示词 + 固定 seed | 零基建、零成本、零新依赖 | 一致性最弱；seed 与场景耦合，换个场景就崩 | ❌ |
| B · 只在提示词里放详细外貌描述 | 实现最简单 | 模型对文字的理解每次都不同，实测不一致 | ❌ |
| C · **定妆照 + 参考图 + 四槽位骨架** | 一致性可用；零训练；可换供应商；机制而非祈祷 | 依赖供应商支持参考图；一致性非 100% | ✅ |
| D · 用定妆照训练角色 LoRA | 一致性最强；边际成本为 0 | 需 ≥8GB 显存；需训练时间；绑死本地 SD | ❌（作为可选路径保留） |
| E · 每次生成后人工挑图、手动替换不合适的结果 | 结果最好 | 不可自动化；Agent 无法自主生活 | ❌ |

### 为什么否掉其他方案

**A / B（只靠提示词或 seed）**：这两条本质是同一件事——**把「一致性」寄托在模型恰好每次都听话上**。
这是 P3 明确反对的「提示词祈祷」。更具体地说：即使某次生成看起来一致，
我们也无法知道下一次是否一致，因为一致性的来源不在我们的控制里。
一个「有时对有时不对」的功能，比一个「明确知道做不到」的功能更糟——
前者会让问题长期被归因为「运气不好」而不被修复。

**D（LoRA）**：技术上是最优解，但它的**前置成本违反本项目的最小依赖原则**。
它要求用户的机器有 ≥8GB 显存——这会把「装好就能跑」变成「先确认你的显卡」。
但因为它实现的是同一个 `ImageProvider` 接口，它可以作为**后加的插件**存在，
不阻塞 v1。所以它是「暂时不选」，不是「永不做」。

**E（人工挑图）**：这直接否定了需求本身（「角色自己生成图片」）。

### 为什么三层机制缺一不可

| 缺哪层 | 后果 |
| --- | --- |
| 缺定妆照（第 1 层） | 没有唯一真源，参考图本身每次都是新的，一致性无从谈起 |
| 缺参考图（第 2 层） | 模型只从文字理解长相，每次理解不同 |
| 缺四槽位骨架（第 3 层） | 模型可能把定妆照的**衣服与背景一起抄过来**——所有照片都在同一个灰色房间里；或者反过来，把脸和衣服一起重新设计 |

**只有三层同时在场，才得到「同一个人，不同的一天」。**

## 后果

### 正面

- 「一致性」从主观形容词变成**可测量的阈值（80%）**。达不到时有明确的下一步（换 provider 或上 LoRA），
  而不是无休止地调提示词。
- 定妆照连同生成参数一起存储，因此**定妆照本身可复现**——这是整个一致性链条的锚点。
- 机制在 `domain/`（纯函数）与 `capability` 编排层，**不依赖任何具体供应商**（P1）。
- 换供应商只需改配置，人设与历史照片的基准都不变（P4）。
- 明确拒绝「不支持参考图却生成人物图」，避免产出「看起来像但其实是别人」的照片。

### 负面

- **一致性仍然不是 100%**。80% 意味着 5 张里有 1 张可能被认成另一个人。这一点必须诚实写在文档与
  界面上，否则用户会在第一次看到不像的照片时认为功能坏了。
- 需要一次额外成本：生成定妆照本身（约 $0.04）以及每次生图多传一张参考图的费用
  （部分按像素计价的供应商会因此涨价）。
- 定妆照是**单点**：一旦丢失或损坏，所有新照片都会失去一致性基准。
  因此 `allow_regenerate_canonical = false` 是默认值，且定妆照必须参与备份。
- 「只有四个槽位」限制了表现力。用户可能想要「换个发型」但发现没有这个槽位。
  这是刻意的取舍：**表现力换一致性**。

### 需要关注

- **什么情况下重新审视本决策**：
  1. 实测一致性持续低于 80%，且已尝试过至少两个支持参考图的供应商 → 应认真评估 LoRA 路径。
  2. 主流生图 API 开始提供「角色 ID / 一致性会话」这类原生能力 → 本方案的第 2 层可以简化。
  3. 用户大量反馈「四个槽位不够」→ 应评估扩展槽位所需的提示词工程与一致性代价。
- **不要把 `build_portrait_prompt()` 挪进插件**。一旦它不在纯函数层，
  第二个生图插件就可以自己拼提示词绕过它，第 3 层机制当场失效。

## 对设计原则的影响

| 原则 | 影响 |
| --- | --- |
| P1 内核无知 | 支持 —— 机制在 `domain/`，具体供应商在 `image.*` 插件，内核不知道任何生图 API 的名字 |
| P2 显式优于隐式 | 支持 —— 定妆照、`appearance_brief`、槽位值全部显式入库，可查可改 |
| P3 机制约束优于提示词祈祷 | **强支持 —— 本 ADR 就是这条原则的应用。** 三层机制取代「请保持人物一致」的提示词 |
| P4 可插拔优于可配置 | 支持 —— 云端与本地 LoRA 实现同一个 `ImageProvider`，切换不改内核与人设 |
| P5 标准库优先 | 中性 —— 需要 `httpx`（已有依赖）；图像转码的 `Pillow` 是**可选**依赖，未安装则存原始格式 |
| P6 可复现 | 支持 —— seed 由 `(persona_id, scene_key)` 派生，同场景可复现；定妆照参数入库 |
| P7 文档与代码同生共死 | 支持 —— 80% 阈值写入设计文档与验收标准，不是口头约定 |
