## 背景

需求是「所有配置都能在 UI 设置界面里设置，并且**每个设置都做好标注**让用户知道这个有什么作用」。

第一部分（能改）是工程问题。第二部分（标注）不是——它是一个**持续性问题**：

> 配置项会不断增加。每加一个，标注就多一份必须维护的东西。
> 而人（包括未来的贡献者，包括 AI 协作者）在加配置项时，**默认不会想起要写说明**。

已有的先例是 `plugin.toml` 的 `[config.<key>]`：它有 `type` / `default` / `description` /
`secret` / `env` / `choices` / `min` / `max`，并由 `ConfigField.describe()` 提供一行摘要。
**插件配置已经做对了。问题在于内核配置没有。**

现状：

```python
@dataclass(frozen=True)
class LLMRoutingConfig:
    strong: str = "openai_compatible"
    cheap: str = "openai_compatible"
    decision: str = "strong"
    expression: str = "strong"
    # ... 没有任何"这个键是干什么的"信息
```

这些字段名对写代码的人自明（`decision` 就是「决策用哪个模型」），
但对打开设置页的用户不自明——他不知道「决策」是什么、换成别的会怎样、
`strong` 和 `cheap` 有什么区别。

约束条件：

1. **不能有第二真源。** 如果说明写在 Web 前端、CLI、文档三处，三处会在一周内开始不一致。
2. **必须能自动化检查。** 「靠自觉写说明」已经被证明在长期不可靠。
3. **必须覆盖插件配置**，否则设置页里内核项有说明、插件项没有，体验割裂。
4. **不能引入新依赖**（P5）。

## 决策

我们要求 **每一个配置项都必须携带 `Setting` 元数据**，
其中 `description`（这是什么）与 `effect`（改了会怎样）**都是必填**，
并通过 **CI 测试强制**。

具体：

1. 定义 `Setting` 数据结构（`kernel/settings.py`），字段包括
   `key` / `label` / `description` / `kind` / `default` / `group` / `choices` /
   `minimum` / `maximum` / `unit` / **`effect`** / `depends_on` / `requires_restart` /
   `danger` / `advanced`。
2. `Choice` 携带 `consequence`：枚举的每个选项都要说明**选它的后果**。
3. 元数据有三个来源，优先级从高到低：内核 `Setting` 声明 → 插件 `plugin.toml` 的 `[config.*]`
   → 兜底推断（标记为「未标注」并在页面顶部计数）。
4. **一枚单一真源，多处渲染**：Web 设置页、`alterego config show`、
   `alterego config explain`、`alterego config schema --json` 全部读同一份元数据。
5. CI 强制三条断言：
   - 每个内核配置字段都有元数据（缺少则测试失败并列出字段名）
   - 每个 `effect` 都是**可验证的因果陈述**（长度 ≥ 8 且不含「可能」「大概」「也许」）
   - 每个枚举的每个选项都有 `consequence`

## 考虑过的方案

| 方案 | 优点 | 缺点 | 是否采用 |
| --- | --- | --- | --- |
| A · 说明写在文档里（`docs/`），设置页链过去 | 零代码 | 设置页仍然看不懂；用户要跳出去读；文档与代码必然漂移 | ❌ |
| B · 说明写在 Web 前端的一个字典里 | 改起来快 | 产生第二真源；CLI 拿不到；插件配置无法覆盖 | ❌ |
| C · 只要求 `description`，不强制测试 | 门槛低 | 三个月后必然有配置项没有说明；「标注」变成部分实现 | ❌ |
| D · **`Setting` 元数据 + 三条 CI 断言强制** | 单一真源；可强制；覆盖插件；零依赖 | 加配置项时要多写几行；`effect` 需要作者真正理解功能 | ✅ |
| E · 从类型与默认值自动生成说明 | 零维护 | 生成的是「daily_message_limit：整数，默认 3」，等于没说 | ❌ |

### 为什么否掉其他方案

**A（写在文档里）**：设置页要解决的是「用户此刻不知道这个键是干什么的」这个**就地**问题。
把他送到文档页面，他读完再回来，问题解决了但体验是断裂的——而且绝大多数人不会跳过去读。
更根本的是，`DESIGN.md` 已经有一个 § 12.1 列配置，再加一份说明就是第三处。

**B（写在前端）**：`05-channels.md` 已确立「没有前端构建步骤，vanilla JS」。
把说明硬编码在 JS 里意味着 CLI 用不了它，而 CLI 的 `config explain` 是同一个需求的另一个出口。
且插件配置由 `plugin.toml` 声明，前端拿不到——除非前端也维护一份，
于是「插件配置的说明」有了两个真源。

**C（只要 `description`，不强制）**：这是最容易走上的路，也是最容易腐烂的路。
判断依据很简单：**现在的 15 个配置 dataclass 有几个字段带说明？零个。**
这不是因为作者懒，而是因为在写 `decision: str = "strong"` 时，
「这个键需要面向用户解释」这个念头不会自然出现。
**没有测试的约定不是约定。**

**E（自动生成）**：「`min_interval_minutes`：整数，默认 90」——这条说明的信息量是零。
用户的问题不是「它是什么类型」，而是「90 分钟是干什么用的、我改成 30 会怎样」。
自动生成说明会把一个**内容问题**假装成**格式问题**解决掉，
反而让「我们有标注了」成为不写真正说明的借口。

### 为什么 `effect` 必须与 `description` 分开且必填

只有 `description` 的设置页是说明书：用户读完知道「这个键控制什么」，
但仍然不知道**该不该改、改了会怎样**。而人打开设置页的动机几乎总是「我想改点什么」。

对比：

| 只有 `description` | 加上 `effect` |
| --- | --- |
| 「每天主动发消息的次数上限」 | 「每天主动发消息的次数上限」<br>**「调高会让它更频繁地找你；设为 0 则它只在回复你时说话。」** |
| 「超出预算时的处理方式」 | 「超出预算时的处理方式」<br>**「选『降级』会改用便宜模型，Agent 继续生活但变笨；选『停止』则彻底不再调用，行为退化为纯规则。」** |

第二列才是用户能据此做决定的信息。所以 `effect` 是必填的，
且测试会拒绝「可能」「大概」「也许」这类模糊表述——
**模糊的 `effect` 比没有 `effect` 更糟**，因为它看起来像有信息。

### 为什么 `Choice.consequence` 也要必填

枚举是设置页里最容易被做坏的一类控件：一个下拉框里列着
`degrade` / `stop` / `warn`，用户不知道选哪个，只能随便试。

要求每个选项自带一句「选它的后果」之后，下拉框本身就成了决策依据。
这条规则的价值在于它**同时服务两类读者**：
用户读它做决定，贡献者在写它时必须先想清楚每个选项到底意味着什么——
**如果作者写不出后果，那通常说明这个选项的设计有问题。**

## 后果

### 正面

- 「每个设置都有标注」从**意图**变成**可被 CI 拦截的规则**。
  漏写说明会导致测试失败并指名道姓地列出字段，修复成本在提交当时是 30 秒。
- 单一真源，Web / CLI / JSON schema 四处渲染永远一致。
- `effect` 强制作者验证自己的理解：写不出「改了会怎样」通常意味着没想清楚这个键该不该存在。
  **这是一条意外收获——它提高了配置项本身的质量门槛。**
- 内核配置与插件配置走同一套渲染器，用户不需要知道边界在哪（P2）。
- 零新依赖（P5）。
- `alterego config schema --json` 顺带提供了 shell 补全与外部工具集成的能力。

### 负面

- **新增配置项的成本上升。** 从 1 行变成 6–8 行（含元数据）。
  这是刻意的摩擦：配置项不是免费的，每一个都要面向用户解释自己是干什么的。
  一个说不出「改了会怎样」的配置项，很可能本来就不该存在。
- `effect` 的质量无法完全自动化。测试只能挡住「空话」和「模糊词」，
  挡不住「写得很具体但是错的」。这需要 review。
- 兜底推断那一层会让「未标注」的键可以存在于设置页里（标黄），
  理论上有腐烂空间。缓解措施是页面顶部的计数——**数字可见就不会被长期忽略**。
- 与 `plugin.toml` 的既有字段有部分重叠（`description` / `type` / `min` / `max`）。
  需要一层适配把 `ConfigField` 映射成 `Setting`，这是必须付出的胶水代码。

### 需要关注

- **什么情况下重新审视本决策**：
  1. 如果 `Setting` 元数据本身超过 900 行上限（文件大小红线）→ 应按分组拆文件。
  2. 如果实测发现「未标注」项长期 > 0 → 说明兜底层太宽松，应考虑改为硬失败。
  3. 如果元数据开始被用于**运行时行为**（而不仅是展示）→ 需要重新评估，
     那会变成第二套配置定义，违反「单一真源」。
     **`Setting` 只能描述配置，不能定义配置**——实际默认值与校验永远以 dataclass 为准。
- **`Setting` 与 dataclass 的漂移风险**：`default` 在两边都有。
  缓解：测试同时断言 `Setting.default == dataclass 字段的默认值`。
  这条断言应该在本 ADR 的实现中一并加上。

## 对设计原则的影响

| 原则 | 影响 |
| --- | --- |
| P1 内核无知 | 中性 —— `Setting` 只是字符串与数字，不含任何具体技术名 |
| P2 显式优于隐式 | **强支持** —— 把「这个键干什么」从作者的脑子里显式化，成为代码里的数据 |
| P3 机制约束优于提示词祈祷 | **强支持** —— 本 ADR 的核心就是：不让「请记得写说明」成为约定，让 CI 拦住它 |
| P4 可插拔优于可配置 | 支持 —— 插件配置与内核配置共用渲染器与元数据格式 |
| P5 标准库优先 | 支持 —— `dataclasses` + `re`，无新依赖 |
| P6 可复现 | 中性 —— 元数据不参与行为 |
| P7 文档与代码同生共死 | **强支持** —— 说明与配置项同文件、同一次提交，物理上无法漂移 |
